# Playable Key Moments — Phase 1 POC evidence

**Programme:** `docs/plan/playable-key-moments-roadmap.md`  
**Implementation PR:** #36 — `feat/playable-key-moments-poc`  
**Scope:** Phase 1 only; no durable career persistence and no continuous 11v11 control.

## Decision summary

Phase 1 has proved the load-bearing engineering hypothesis: a real Pitch match can stop after authoritative phase preparation but before terminal shot resolution, accept bounded normalized user intent, commit the result once to the existing authoritative ledger, and resume through the normal discipline/injury/substitution flow without creating a second match engine.

The selected renderer for the POC is **Three.js 0.185.1 (MIT)**. The PlayCanvas comparison spike was removed from the production graph after the decision.

### Why Three.js won the bounded renderer comparison

Both candidates rendered the same repository-owned procedural scene contract, so the comparison did not depend on different models or animation assets.

| Criterion | Three.js 0.185.1 | PlayCanvas 2.22.0 | Decision |
|---|---:|---:|---|
| Licence | MIT | MIT | tie |
| POC adapter production chunk before engine load | ~5.1 kB | ~5.2 kB | tie |
| Published minified ESM engine payload | **356.98 kB** | **2.35 MB** | Three.js |
| Extra engine/editor workflow required | none | none | tie |
| Capability needed by this POC | sufficient | sufficient | tie |
| Adapter complexity for this scene | smaller/simpler | broader engine lifecycle | Three.js |

Published payload evidence:

- Three.js exact-version jsDelivr listing: `https://cdn.jsdelivr.net/npm/three@0.185.1/build/` (`three.module.min.js` = 356.98 kB).
- PlayCanvas exact-version jsDelivr listing: `https://cdn.jsdelivr.net/npm/playcanvas@2.22.0/build/` (`playcanvas.min.mjs` = 2.35 MB).

## Asset and animation provenance

Phase 1 intentionally uses **no downloaded football player, goalkeeper, stadium or animation assets**. The pitch, goal, ball, shooter, defender and goalkeeper are created procedurally in repository code. Strike, run-up, defender lunge, keeper dive and recovery are deterministic transforms generated by `playableMomentsPocScene.js`.

The final Phase 1 polish improved the generated footballers without changing that provenance boundary: realistic adult proportions replaced the original oversized block figures; tapered/rounded torso and limbs, articulated knees/elbows, socks, boots, gloves, hair and simple facial direction were added; the goalkeeper now uses a recognisable ready stance and a grounded capped jump/dive lift rather than translating the whole body toward high shots.

Consequences:

- no paid asset is present;
- no Blender/manual animation pipeline is required;
- no third-party model/animation licence needs to be carried into Phase 2;
- the only third-party runtime input is the exact-version MIT Three.js engine.

This is deliberate for the POC. Phase 2 may introduce approved free/CC0 production assets only after a provenance manifest and deterministic conversion pipeline are defined.

## Authoritative continuation contract proved

The POC introduces a three-stage domain seam:

1. `prepareAuthoritativePhase()` resolves possession, route, actors, success and chance context but does **not** decide the shot finish.
2. `buildPlayableMoment()` projects a deterministic pre-outcome scene from that prepared context.
3. `commitAuthoritativePhase()` resolves either the unchanged automatic finish or bounded interactive attack/goalkeeper intent and produces the existing authoritative ledger/event contract.

`resolveAuthoritativePhase()` remains the compatibility wrapper around prepare + commit. Normal Quick Sim / Watch callers therefore keep the established automatic path.

`simulateMatchSegment()` can suspend only when explicit POC control requests a **single phase** and an eligible controlled-team moment is prepared. The suspension snapshot contains the already-allocated phase/RNG/fitness state but publishes none of it. `resumePlayableMatchPhase()` restores that snapshot, commits the shot once, then runs the normal post-action discipline/injury/substitution logic.

The synthetic training drills are intentionally separate from the production match resolver. Their tutorial rules make the interaction learnable without changing real-match probabilities or Quick Sim / Watch parity.

## Synthetic drill behaviour

### Attacking drill

- ordinary on-target attempts are saved;
- attempts outside the goal frame miss;
- a **special finish** scores when the player combines sufficient power and timing with placement into either highlighted top corner;
- the renderer projects the actual pointer/touch endpoint onto the 3D goal plane before normalising aim, so visually touching a top corner maps to that top corner rather than to an approximation based on the entire canvas;
- gold target rings and UI guidance make the special-finish rule visible rather than hidden.

### Goalkeeper drill

- incoming shots cycle deterministically through six non-centre zones: top-left, top-right, low-left, low-right, mid-left and mid-right;
- a cyan 3D target cue appears before the strike and the UI labels the destination;
- a correct read uses a deliberately forgiving synthetic save radius so the drill teaches positioning instead of requiring a blind perfect guess;
- choosing the wrong side still results in a goal;
- each attempt advances through a dedicated `Next keeper shot` flow.

These rules are POC/tutorial-only and do not replace the authoritative open-play shot resolver.

## Final code-review findings closed

The Phase 1 review loop found and fixed defects rather than accepting the first green-looking implementation:

- Svelte 5 UI state was converted to explicit reactive state and current event syntax;
- pointer surface accessibility and keyed rendering were corrected;
- browser globals were scoped explicitly so lint remains strict;
- striker strike and goalkeeper dive include an explicit recovery phase rather than freezing in their terminal pose;
- dynamic scene rebuild removes/disposes pitch, goal-line and goal geometry before replacing it;
- actual goal-plane pointer projection now drives visible aiming;
- generated footballer proportions/anatomy and goalkeeper stance were materially improved;
- high goalkeeper saves now use a capped grounded lift with body/arm reach instead of unrealistic whole-body vertical translation;
- the losing PlayCanvas spike was deleted after the renderer decision.

## Production-load isolation

The POC is mounted only when `?playable-poc=1` is present. `src/main.js` dynamically imports `PlayableMomentsPoc.svelte`, and that component dynamically imports the Three.js adapter. The 3D renderer is therefore absent from ordinary management startup.

The final reviewed Vite build emitted the POC independently from the management bundle:

- `PlayableMomentsPoc` CSS: **5.40 kB** (1.67 kB gzip);
- Three.js POC adapter: **9.08 kB** (3.29 kB gzip);
- POC component: **21.90 kB** (8.26 kB gzip);
- no PlayCanvas adapter chunk exists in the final build.

The external Three.js engine is requested only after the query-gated POC and renderer adapter are loaded.

## Completion classification

**Phase 1 engineering / architecture POC: PASS.**

The implementation, authoritative continuation design, chosen renderer, synthetic training UX, procedural character presentation, provenance constraints, lazy-load boundary, automated regressions, balance calibration and deployability all satisfy their Phase 1 engineering gates. The POC is complete enough to hand to product review without further Phase 1 code expansion.

The roadmap deliberately made rendered/mobile/game-feel observation a human-observable acceptance item. This coding-agent environment cannot resolve/open the deployed Worker in an interactive browser, and the repository explicitly prohibits adding browser/E2E automation. Therefore this record does **not** fabricate frame-time, touch-device or subjective animation-quality measurements.

That final product-review observation is a **manual sign-off**, not unfinished engineering work. Before beginning persistence-heavy Phase 2, open the preview on a real phone/browser and record:

- visible agreement between miss/save/goal and ball/keeper contact;

No architecture or Phase 1 feature code should be added merely to collect that sign-off; the instrumentation is already in the POC surface.
