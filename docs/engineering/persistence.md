# Persistence and server contracts

Read before save, IndexedDB, migration or cloud changes. Paths are repository-relative.

### Persistence / career slots — P0 foundation

- IndexedDB access lives in `src/modules/db.js`; domain code should not open ad-hoc databases.
- Save envelope is **V2** with `schemaVersion` and stable `slotId`. Existing V1 `.pitch` saves migrate explicitly; future persistent changes must extend the ordered migration path rather than rely on ad-hoc backfills.
- Multiple careers are isolated by slot:
  - `legacy` keeps the original physical `pitch_fc` database so pre-P0 browsers remain discoverable;
  - deleting/resetting the legacy career **clears its stores in place** — do not physically delete/recreate that compatibility database;
  - generated career slots use separate `pitch_fc_slot_<slotId>` databases and may be physically deleted.
- New Career allocates an isolated slot only when a career/import is actually committed. Backing out must leave the existing active career untouched.
- Career Menu metadata contract: manager, club, season, league, league position, gameweek, last played, save schema version; UI adds active state separately.
- Local export/import and cloud save use the same versioned envelope/slot metadata contract.
- Envelope export reads every store in one readonly transaction, so a concurrent match/rollover cannot mix checkpoints between the save, players and fixtures.
- Cloud save API/D1 is slot-aware: rows are keyed by `(user_id, slot_id)`; pre-P0 cloud rows migrate to `legacy`.
- Cloud blobs above 750,000 ASCII bytes use reserved `<slotId>.chunk.<index>` rows in the existing table. Public slot IDs exclude dots. A versioned head manifest and every chunk publish in one D1 batch; replacement removes old chunks in that same batch. Reads select head/chunks in one snapshot and validate count, lengths and revisions before returning the original opaque blob. Lists exclude internal rows, and deletion uses an exact user/slot prefix. Single-row backups remain readable; no schema migration is needed. Keep the chunk-aware Worker when rolling back client changes after larger backups have been written. Capacity is 40 MB compressed/base64, with an actionable file-export message above that limit; blob requests allow 60 seconds for transfer.
- P1 legacy/current careers backfill living-world state through the existing migration/backfill path; do not require users to destroy a P0 career to gain the world model.
- Living-world backfill compacts only already-applied background cup records. The player/projection checkpoint clears their transient football payload atomically with its apply-once flag; pending records remain recoverable. Scores, seeds, versions, goals and competition history remain available without retaining weekly fitness updates and full tactical objects in the active save.
- Applied background league records likewise discard consumed fitness updates and non-goal events. Scores, seeds, tactics, statistics and goals remain; current-club fixtures, prior managed tactical reports, pending projections and future compaction versions retain full payloads. The apply-once flag and player/standing projections still share one transaction; boot backfill only touches already-applied records.
- P3 uses additive, idempotent player-row/domain backfills and does not increment `DB_VERSION` merely to add fields to existing rows. Preserve that pattern for compatible player-contract extensions.
- Physical database version 6 serializes player rows through the reversible V2 codec in `playerStorageCodec.js`. An ordered versionchange cursor upgrade publishes every existing row together or leaves the previous database version intact on abort. Stored `id`/`teamId` remain canonical for the existing key and club index; `db.js` encodes every player write and decodes every player read, including atomic transfer reads and envelope snapshots. The game and logical V2 file/cloud envelopes receive canonical player objects, never the wire wrapper. V1 rows are decoded before the V6 cursor upgrade encodes V2 rows, and legacy unencoded rows remain readable. V2 uses a compact key-order string and dense values without changing field order. Preserve both published dictionaries and tags; future incompatible codecs need a new decoder/version and must reject unsupported versions before rewriting data. Unknown fields, field order, primitive types, arrays and within-row shared references are retained. This physical serialization change requires a database version, unlike compatible additive domain fields.
- Physical database version 7 applies that same graph representation to season archives through `seasonStorageCodec.js`. Its ordered cursor upgrade leaves V6 players untouched, preserves every archive value and ID, and commits inside the existing versionchange transaction. Season reads and V2 snapshots decode; season writes/adds encode. Native auto-increment IDs remain visible in the same canonical field position. Keep the current physical version (V8), its index and both decoders when rolling back game features after a browser career has upgraded; an older client cannot open a newer physical database. Logical file/cloud exports remain V2 and contain neither physical wrapper.
- Physical version 8 adds `players.by_injury` over the compact row's numeric `i` projection (`Number(Boolean(player.injured))`). The ordered player cursor upgrade populates the index atomically; every later player write keeps it current, and decoding validates that projection when present. Medical recovery reads only key 1, including injured unattached players, and retains the existing apply-once clock. Keep physical version 8, its index and both decoders on feature rollback. Atomic transfer settlement reads the save, clubs and history plus named target/exchange players and the seller's indexed squad within its original transaction; unrelated players cannot affect it. Numeric legacy IDs remain reachable from string deal references. Seller squad/keeper floors apply when registration leaves, including ordinary loans; renewals and loan-backs that keep the registration are permitted.
- Player persistence shares identical flat registration/academy snapshot objects within each row. IndexedDB structured cloning preserves these references, reducing duplicate storage while JSON exports and every history value remain identical. `sharePlayerHistorySnapshots` leaves distinct snapshots intact; consumers copy evidence before changing it. `compactPlayerHistoryPayload` also omits known zero counters (history readers already default missing counters to zero) and clears unused academy evidence on senior, loan and free-agent spells; actual academy spells, nonzero counters, unknown fields, IDs, clubs, dates and reasons remain. All player write boundaries and living-world boot backfill apply this idempotent representation, including JSON imports; no schema or lifecycle version changes. Seasonal history projections must remain identical across compaction.
- Managed match completion uses `db.commitMatchEventAtomic`: canonical league fixture or cup participant rows, cup progress, Manager DNA and queue consumption commit together. Failure aborts the whole checkpoint. The transaction re-reads the save and rejects a changed queue head.
- `pendingEventsWeekKey` identifies an initialized queue for the current season/week, including an empty queue awaiting world closeout. Its absence on older saves uses the normal queue builder; advancing the world week clears it. `lastResolvedEvent` retains one compact receipt so retrying a committed Broadcast result cannot consume the following event. These optional V2 fields do not create another save lifecycle or retain an unbounded result history.
- Season rollover runs inside `db.runSeasonRolloverAtomic`. All store reads and writes use the same transaction, including asynchronous domain work; aborting preserves the outgoing calendar, players, finances and history together. Keep rollover helpers on the normal database accessors so they participate in that transaction.
- Resignation and accepted club handover use `db.runCareerTransitionAtomic`, the same transaction owner. Manager status, club ownership and the saved vacancy or pending handover commit together; a failed write keeps the previous employment state and allows the handover to retry safely.
- Historical player detail is bounded: the latest completed world season stays detailed; three recent completed seasons keep individual contributor and academy totals. Earlier seasons retain world leaders/award winners, and every season keeps tables, awards, club summaries and detailed rows for that season's managed club. `compactHistoricalSeason` preserves retained IDs and registration clubs and never mutates its input. `omitIdleUnattachedHistory` also avoids repeating idle free agents in the latest archive; it retains any senior/academy contribution, club registration, transfer, award or injury and leaves retained rows intact. Rollover compacts older records in the existing transaction. `ensureSeasonHistoryCompaction` backfills old/imported careers once during `initApp`, keeping retained latest rows detailed and publishing its version-three marker atomically with the compacted rows; future versions are left alone. Do not delete active players to reduce archive size.
- Import validates the envelope before changing data, then clears and restores the target slot in one transaction. A failed restore preserves that slot's existing contents and restores the prior active-slot pointer, including failure to open the destination database.
- Empty-device cloud recovery discovers generated remote slots and restores the latest backup only while no local career exists. Recheck local state after network waits. Uploads currently replace a slot's backup; simultaneous devices have no conflict resolution, so the UI advises using one device at a time.

## 4) Server/cloud boundary

- `functions/` is Pitch's only server-side code: Worker request routing, Google OAuth/session support and D1 cloud saves.
- Pitch remains playable without an account; server authority is not required for core single-player simulation.
- `functions/_worker.js` manually dispatches API routes then falls through to `env.ASSETS.fetch(request)`.
- D1 migrations live in `migrations/`; P0 added the slot-aware saves migration. Treat migration order as production data history.
- Never put secrets in the repo. Cloudflare bindings/secrets are deployment configuration.
